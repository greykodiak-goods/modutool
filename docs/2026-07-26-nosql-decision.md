# SQL vs NoSQL 판단 기준 + 이 프로젝트의 결정 (2026-07-26)

> 대표 질문: "NoSQL은 join·group by가 불리한가? 어떤 프로젝트일 때 할지 말지."
> 결론: **불리한 것 맞다.** 다만 그 약점이 이 프로젝트(modutool)에는 거의 안 닿고, awning-ops에는 정통으로 닿는다.
> → **modutool = NoSQL(Convex), awning-ops = SQL(Postgres) 유지.**

## 1. 무엇이 실제로 불리한가 (정확히)

### JOIN — "불편하지만 치명적이진 않다"
- SQL: 쿼리 하나로 엔진이 최적 알고리즘(해시/머지 조인)을 골라 처리. 쿼리 플래너가 알아서 함.
- 문서DB: 조인 문법이 없다. 문서를 가져온 뒤 관련 문서를 하나씩 조회하는 코드를 **직접** 쓴다(N+1).
- **Convex의 완화 요인**: 쿼리 함수가 DB 런타임 *안에서* 실행돼 조회마다 네트워크 왕복이 없다.
  일반 문서DB의 N+1보다 훨씬 싸다. 그래도 "내가 짜는 O(N) 루프" vs "플래너가 최적화하는 선언형 조인"의 차이는 남는다.

### GROUP BY / 집계 — **이쪽이 진짜 약점**
- SQL: `select tool, count(*) ... group by tool` 한 줄. 인덱스·병렬 스캔으로 처리하고 결과만 작게 반환.
- 문서DB: 집계 엔진이 없다. 문서를 애플리케이션으로 **전부 읽어와서** JS로 세야 한다.
- Convex는 쿼리 1회당 **읽기 상한**(문서 수·바이트)이 있어서, 로그가 수만 건을 넘으면 "최근 30일 집계"가 그냥 **깨진다**.
- 표준 해법은 **쓸 때 미리 세어두기**(롤업/카운터). 즉 읽기 최적화를 쓰기 시점으로 옮긴다.
- 대가: **집계 차원을 미리 정해야 한다.** "어제 유입출처 × 언어별 실패율" 같은 즉석 질문을 SQL처럼 던질 수 없다.

### 한 줄 요약
> SQL은 **나중에 아무 질문이나** 할 수 있다. NoSQL은 **미리 정한 질문에만** 싸게 답한다.

## 2. 언제 NoSQL / 언제 SQL

| NoSQL이 맞는 프로젝트 | SQL이 맞는 프로젝트 |
|---|---|
| 접근 패턴이 단순·고정 (id로 읽기, 인덱스로 목록, append 로그) | 임의 분석·리포팅이 업무의 핵심 |
| 실시간 구독(reactive)이 가치 있음 | 엔티티가 여러 겹으로 얽힘(주문×품목×재고×정산) |
| 스키마가 자주 바뀌고 문서 형태가 제각각 | 여러 테이블에 걸친 트랜잭션 정합성 필요 |
| 서버리스/엣지, 커넥션풀·마이그레이션 운영을 없애고 싶음 | GROUP BY 대시보드가 계속 늘어남 |
| 쓰기 많은 append-only 로그(+ 롤업으로 집계) | BI 도구·SQL 클라이언트·내보내기 생태계가 필요 |

**판별 질문 3개** — 하나라도 "예"면 SQL 쪽으로 기울어라:
1. 6개월 뒤 "이런 것도 뽑아봐" 같은 **예상 못 한 집계 요청**이 올 것 같은가?
2. 한 화면을 그리는 데 **3개 이상 엔티티를 조인**해야 하는가?
3. 여러 테이블을 **한 트랜잭션으로 묶어야** 하는가?

## 3. 우리 두 프로젝트에 적용

### modutool (ThisIsMy Tools) → **NoSQL(Convex) 확정**
- 데이터: `toolEvents`(append-only 로그) / `profiles`(사용자 1:1) / `adminUsers`(화이트리스트).
- **조인이 사실상 0.** 집계는 백오피스 대시보드 **한 곳**뿐이고, 그 화면은 정해진 지표만 본다.
- 판별 질문 3개 전부 "아니오".
- 덤: Supabase 무료 활성 2개 한도 때문에 경매 DB와 번갈아 죽는 문제가 **구조적으로 사라진다**.
- **약점 대응(이번에 구현 완료)**:
  - `dailyStats` 롤업 테이블 신설 — `logEvent`가 쓸 때 `(일자×도구×결과)` 카운터를 증분.
  - 대시보드의 총계·도구별·일별·뷰 추이는 **롤업에서** 읽는다 → 로그가 수백만 건이어도 읽는 문서 수 일정.
  - 사유·유입출처·인기페이지는 차원 조합 폭발을 피하려 **최근 5,000건 상한 스캔**으로 계산하고,
    잘리면 `sampled=true`로 백오피스에 명시(조용한 절단 금지).
  - 트래픽이 아주 커지면: 롤업 키에 샤드 접미사를 붙여 쓰기 경합 분산(코드 주석에 명시).

### awning-ops → **SQL(Postgres) 유지 — 옮기면 안 됨**
- 데이터: orders × order_items × products × inventory × ad_report_rows × deposit_ledger …
- 일상 업무 자체가 조인+집계다. 실제 사례: 72시간 스프린트 실사에서 쓴 쿼리가 전부
  "상태별 GROUP BY", "일자별 소진 추이", "캠페인별 ROAS 집계", "엔비전달 적체 합산"이었다.
- 판별 질문 3개 전부 "예" → NoSQL로 옮기면 그 분석을 전부 손으로 다시 짜야 하고,
  미리 정하지 않은 질문은 아예 못 던지게 된다. **명백한 손해.**

### 정리
> 도구사이트는 "정해진 지표만 보는 로그" → NoSQL.
> 운영 ERP는 "매번 새로운 질문을 던지는 장부" → SQL.
> 하나로 통일하려 하지 말 것. 성격이 다르다.

## 4. 시크릿 관리 — Doppler (awning-ops 패턴 이식)

ops에서 검증된 패턴을 modutool에 그대로 도입:
- **Doppler 우선 → GitHub Secret 폴백**(무중단). CLI는 `dopplerhq/cli-action@v3`, `continue-on-error`.
- 값은 `add-mask` 후 `GITHUB_ENV`로 후속 스텝 전달.
- `doppler-check.yml`: 값은 절대 출력하지 않고 **키 이름·존재 여부만** 검증(ops와 동일).
- 적용 지점: `convex-deploy.yml`의 `CONVEX_DEPLOY_KEY`.
- **현재 상태**: modutool 레포에 `DOPPLER_TOKEN`이 아직 없음(계정이 조직이 아니라 ops 레포 시크릿이 공유되지 않음).
  → 이 토큰 **하나만** 넣으면 앞으로 Convex 키·구글 OAuth·애드센스 ID까지 전부 Doppler에서 조달된다
  (개별 시크릿을 레포마다 등록할 필요가 사라짐).
