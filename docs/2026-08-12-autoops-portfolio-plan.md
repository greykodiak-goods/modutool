# 다수 서비스 자율운영(AutoOps) — 내가 쓸 것을 만들면서 지원받는 구조 (2026-08-12)

> 대표 지시: "AI 오케스트라 서비스나, 다수의 서비스를 모니터링하고 관리하는 AI 툴,
> 다수의 마케팅을 자동운영하는 툴, AI 자가 발전하는 시스템 이런쪽으로 해봐.
> 내가 서비스 다작하면서 쓰게 될 것들 미리 만들면서 사업 지원받게."

---

## 0. 먼저 — 이 방향이 앞선 후보들과 결정적으로 다른 점

지금까지 계속 충돌했던 두 요구가 **처음으로 같은 방향을 가리킨다.**

| 요구 | 이 방향에서 |
|---|---|
| **당사자성** ("내가 아는 분야") | **첫 사용자가 우리 자신이다.** 안 만들면 우리가 못 버틴다 |
| **펜시함·시장** | AI 오케스트레이션 · 자율운영 · 자가발전은 지금 가장 위쪽 키워드 |

F1(AI 거버넌스)이 반려된 이유가 당사자성 부재였다. **도그푸딩은 그 약점을 정확히 메운다.**
그리고 이건 첫 문서(`autoops-grant-plan`)의 축과 같은데, 그때 약했던 사업화 서술이
"**내가 쓸 것을 만든다**"로 해결된다.

### 대표님이 말한 4개는 4개 제품이 아니다 — 하나의 루프의 4단계다

```
      ┌─────────────────────────────────────────────────────────┐
      │                                                         │
  관측(②모니터링) → 진단(④자가발전) → 판정 → 실행(④자동수정+게이트)
      │                                              ↓          │
      └────────────  유입 조정(③마케팅 자동운영) ◄────┘          │
                              ↑                                 │
                    ①오케스트레이션 = 이 루프를 굴리는 실행 계층  │
                              └─────────────────────────────────┘
```

**중요: ①오케스트레이션은 제품이 아니라 수단이다.** 이걸 제품으로 팔면 진다(2절 참조).
4개를 따로 팔면 전부 지고, **4개를 잇는 루프는 아무도 팔지 않는다.** 여기가 우리 자리다.

## 1. 시장 근거 — 지금 벌어지고 있는 일 (확인된 사실)

| 사실 | 값 |
|---|---|
| 바이브코딩의 위상 | 2025년 밈에서 벗어나 **2026년 기본 워크플로**가 됨 |
| **YC 최신 배치** | **코드의 95%가 AI 생성** |
| "80% 벽" | 눈에 보이는 프론트엔드는 빨리 완성되고, **백엔드·보안·유지보수가 나머지를 다 먹는다** |
| 앱 1개 운영 비용 | 호스팅·DB·인증 **월 $45~80** + **40~100시간 이상의 시간** |
| 1인 빌더의 특성 | 긴 셋업은 참지만 **깨진 런치는 못 참는다** |

> **한 문장 명제: 만드는 비용은 붕괴했는데 운영 비용은 그대로다.**
> **그래서 병목이 "생산"에서 "운영"으로 옮겨갔다.**

이 명제는 펜시하면서 **동시에 사실이다.** 지원사업·투자에서 이런 명제가 가장 강하다.
그리고 서비스 10개를 굴리면 인프라비만 월 $450~800이고, 시간은 곱해진다 —
**여기가 우리 가격의 근거가 된다.**

## 2. ⚠️ 선점 조사 — 4개를 따로 보면 전부 점유돼 있다

앞선 문서들에서 조사를 뒤에 배치해 시간을 버린 적이 있으므로 이번엔 먼저 적는다.

| 대표님이 말한 것 | 이미 있는 것 | 판정 |
|---|---|---|
| **① AI 오케스트레이션** | LangGraph · CrewAI · AutoGen · Temporal · n8n · Dify, 그리고 **Claude Code 자체** | **✗ 단독 제품 불가** |
| **② 다수 서비스 모니터링** | Sentry · Datadog · Better Stack · PostHog | **✗ 단독 제품 불가** |
| **③ 마케팅 자동운영** | 광고 자동화 도구 다수 + 대행사. 게다가 앞선 조사대로 **카카오모먼트 API는 공식대행사 협의 광고주만** 접근 가능 | **△ 제약 있음** |
| **④ AI 자가발전 (자동수정)** | **Sentry Seer** — 관측→근본원인 분석→**Autofix**→코드리뷰까지 이미 제공. **2026년 1월 무제한 정액제**로 전환. "24시간 대기하는 엔지니어처럼 배후에서 찾고 알리고 고친다"가 그들의 목표 문구 | **✗ 정면 승부 불가** |

**④가 특히 중요하다.** "AI가 스스로 고친다"를 주제로 잡으면 Sentry Seer와 정면 비교되고,
무제한 정액제까지 나온 상태라 1인이 이길 수 없다. **이 사실을 모르고 계획서를 쓰면 발표에서 끝난다.**

## 3. 그런데 남아 있는 구멍이 정확히 네 개 있다

### 구멍 ①: **에러가 아닌 실패 (silent failure)**

Sentry류는 **예외를 잡는다.** 그런데 우리 실화는 이랬다:

> 사용자가 "이런 거 왜 압축 안 돼"라고 물어왔다.
> **코드는 정상 동작했고, 예외도 없었고, 로그는 깨끗했다.** 이미 압축된 파일이라 더 줄지 않은 것이었다.
> 즉 **프로그램은 성공했고 사용자는 실패했다.**

> **예외 기반 도구는 이걸 구조적으로 못 잡는다.** 그래서 `telGuessReason()`이 태어났다.
> 이게 우리가 이길 수 있는 첫 번째 구멍이고, **실화에서 나온 것**이다.

### 구멍 ②: **존속/중단 판정 — 아무도 "이 서비스를 접어라"를 말해주지 않는다**

Sentry는 버그를 고쳐준다. Datadog은 지표를 보여준다. **그런데 "이 제품을 계속할 것인가"는
어떤 도구도 답하지 않는다.** 서비스가 5개일 때는 감으로 되지만 50개면 안 된다.
그리고 서비스당 사용자가 적어 **개별로는 통계적 판단이 불가능하다** — 이게 연구과제가 된다(5절 R1).

### 구멍 ③: **유입과 성과가 끊어져 있다**

관측 도구와 광고 도구가 분리되어 있어 **"이 광고가 실제로 목적을 달성한 사용자를 데려왔나"**를
아무도 잇지 않는다. 우리는 같은 판정 엔진을 광고에도 쓴다 —
**그래서 ③(마케팅 자동운영)이 독립 제품이 아니라 루프의 한 축이 된다.**

### 구멍 ④: **전제가 다르다**

| | 기존 도구 | **우리** |
|---|---|---|
| 제품 수 | **1개** | **N개** |
| 사람 | **팀 있음** | **0명** |
| 데이터 | SaaS로 전송 | **비식별·온디바이스** |

전제가 다르면 가격·UX·판단 방식이 전부 달라진다. **기존 도구가 "N개 + 0명"을 지원하지 않는 이유는
못 해서가 아니라 그런 고객을 겨냥하지 않았기 때문이다.**

## 4. 제품 정의

> **주제명(추천): "비에러 실패를 관측하고 존속·개선을 자동 판정하는 다수 서비스 자율운영 AI"**
> 짧게: **서비스 포트폴리오 자율운영(AutoOps) 플랫폼**

| 모듈 | 내용 | 대표님이 말한 것과의 대응 |
|---|---|---|
| **M1 비식별 결과 관측** | 예외가 아니라 **"사용자가 목적을 달성했는가"**를 기록. 개인정보·파일 미수집 | ② 모니터링 |
| **M2 실패원인 자동 분류** | 비식별 라벨(`이미 압축된 파일`·`암호 걸린 문서`·`메모리 초과`·`미지원 코덱`)로 분류 | ④ 자가발전(진단) |
| **M3 포트폴리오 판정** | 서비스·기능 단위로 **고칠까 / 버릴까 / 키울까**를 판정. 저표본에서도 작동 | (없던 것 — **핵심 차별**) |
| **M4 수정 실행 + 회귀 게이트** | 수정안은 자동, **승인은 게이트가** 한다. 미통과 시 자동 폐기 | ④ 자가발전(실행) |
| **M5 유입 자동 조정** | 광고 단위 CPA를 M3 엔진으로 판정해 자동 ON/OFF·증액 | ③ 마케팅 자동운영 |
| (기반) 실행 계층 | 위 모듈을 굴리는 에이전트 오케스트레이션 | ① — **제품이 아니라 수단** |

**M3가 제품의 심장이다.** M1·M2·M4는 기존 도구와 겹치는 축이 있지만, M3는 **아무도 안 만든다.**

## 5. 연구과제 (디딤돌용) — 정량목표까지 이미 정리돼 있다

`2026-08-12-autoops-grant-plan.md`의 R1~R3을 승계하고 R4를 추가한다.

| # | 과제 | 정량목표 |
|---|---|---|
| **R1** | **극저빈도 신호에서의 존속/중단 판정** — 서비스당 월 200명이면 A/B 하나 못 돌린다. 계층적 부분풀링(empirical Bayes) + 저표본 밴딧 | 1개월 시점 판정을 3개월 실적과 대조해 **정밀도·재현율 ≥ 0.8** |
| **R2** | **개인정보 비수집 상태의 실패원인 추정** — 파일도 세션도 사용자도 수집하지 않고 원인을 분류 (구멍 ①이 여기) | 자동분류 **macro-F1 ≥ 0.8** |
| **R3** | **자동수정 → 회귀 게이트** — 수정은 자동, 승인은 규칙 | **무수정 병합률 ≥ 40%**, **자동병합 회귀사고 0건** (후자가 더 중요) |
| **R4** (신규) | **유입-성과 연결 판정** — 광고 단위별 CPA를 저빈도에서 판정 (R1의 응용) | 판정 후 CPA 개선률, 오차단율 |

**연구가 아닌 것도 분리해 적는다** (계획서에 그대로 넣을 표):

| 항목 | 성격 |
|---|---|
| 배포 자동화, 대시보드, 알림, 오케스트레이션 실행 계층 | **일반 개발** — 신규성 주장 금지 |
| LLM 호출로 수정안 생성 | **응용 통합** — 신규성은 생성이 아니라 **게이트 설계**에 있다 |
| **R1·R2·R4의 저빈도 판정, R3의 안전 게이트** | **연구 성분 실재** |

## 6. 도그푸딩의 힘 — 그리고 그 함정

### 힘

- **"첫 고객이 우리"는 T(팀)와 S(실현가능성)를 동시에 채운다.** 1인 기업 최대 약점을 덮는다
- 도구 40개가 **실증 시험대**로 이미 존재한다. 새로 만들 필요가 없다
- **개발 속도가 빠르다.** 매일 쓰는 물건은 요구사항을 물어볼 필요가 없다
- 증거가 **자동으로 쌓인다** — 우리가 쓰는 동안 R1~R4의 데이터가 생성된다

### 함정 (반드시 대비)

1. **"자기가 쓸 거 만든 것"으로만 보이면 시장성 점수가 깎인다.**
   → **외부 고객 인터뷰로 "남도 이 문제가 있다"를 증명해야 한다.** 이게 8월 1번 과제
2. **우리 특수 상황에 과적합된다.** → 초기에 외부 고객 1~3곳을 반드시 넣는다
3. **실증 규모를 과장하면 안 된다.** 우리는 지금 "서비스 40개"가 아니라
   **"사이트 1개 안의 도구 40개"**다. 이 차이를 정직하게 표현해야 한다
   (계획서에 "40개 서비스 운영 중"이라고 쓰면 확인되는 순간 신뢰가 무너진다)

## 7. 고객과 가격

### 고객 (1인 개발자를 1차로 두지 않는다)

| 순위 | 고객 | 이유 |
|---|---|---|
| **1차** | **앱·웹 스튜디오 / 에이전시** (법인, 프로젝트 수십 개) | **법인이라 지출 결정이 된다.** 사람 수에 비례해 늘던 운영 비용을 줄이는 게 곧 마진 |
| 2차 | 사내 도구를 다수 보유한 기업 | 아무도 안 쓰는 사내 도구를 못 버리고 유지비만 낸다 |
| 3차 | 1인·소수 개발사 (앱 10~100개) | 문제는 가장 크지만 **지불의사가 가장 낮다** (8절 리스크 참조) |

### 가격 근거

앱 1개 운영에 **월 $45~80 + 40~100시간**이 든다(1절). 서비스 10개면 월 $450~800.
→ **구독 [가정] 월 $29~99** (관리 서비스 수 구간제). 논리는 이렇다:
**"서비스 1개 인프라비 수준으로 N개의 운영 판단을 산다."**
오픈소스 셀프호스팅 옵션도 검토한다(Langfuse가 그 방식으로 성장한 선례).

## 8. 정직한 약점 5개

1. **Sentry Seer가 무제한 정액제로 내려왔다.** 진단·자동수정 축에서 정면 비교되면 진다.
   → **서술을 반드시 "에러가 아닌 실패 + 포트폴리오 판정"에서 시작한다.** "우리도 자동수정합니다"로 시작하면 그 순간 진다
2. **도그푸딩 과적합** (6절)
3. **⚠️ 1인 개발자 시장의 지불의사가 낮다.** 인디 개발자는 월 $29도 아낀다.
   → 그래서 **1차 타깃을 스튜디오·에이전시(법인)로 둔다.** 이게 이 방향의 최대 리스크이고 8월 검증 대상
4. **자동수정이 사고를 내면 사업이 끝난다.** → **게이트가 제품의 핵심이자 마케팅 포인트**다.
   "자동으로 고칩니다"가 아니라 **"게이트를 못 넘으면 버립니다"**를 앞세운다
5. **오케스트레이션 계층을 직접 만들면 시간을 다 쓴다.** → 기존 도구(LangGraph 등)를 쓰고
   우리는 M3에 집중한다. **바퀴 재발명 금지 원칙과 같다**

## 9. R1(경매)과 비교 — 무엇이 유리하고 무엇이 불리한가

정직하게 양쪽을 적는다. 결정은 대표님 것이다.

| | **AutoOps (이 방향)** | R1 경매 낙찰 후 운영 |
|---|---|---|
| 당사자성 | **★★★★★ 매일 쓴다** | ★★★ 시스템 구축 경험 |
| 펜시함 | **★★★★★** | ★★★★ |
| 개발 속도 | **★★★★★ 요구사항을 물을 필요 없음** | ★★★ |
| **지불의사 검증** | **★★ 미검증 — 최대 리스크** | **★★★★★ 이미 연 92만~115만원 내는 시장** |
