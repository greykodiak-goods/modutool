## 1. 최우선 — 색인 확보 (지금 가장 저평가된 작업)

도구를 아무리 잘 만들어도 색인이 안 되면 0이다. 지금 확인 안 된 것들:

1. **Search Console 등록 자체가 안 돼 있다.** 색인 여부·색인 제외 사유·검색어를 아무도 모른다.
   github.io 하위 경로는 도메인 소유권 확인이 안 되므로 **URL 접두어 방식**으로 등록해야 한다.
2. **github.io 서브패스의 구조적 한계**: 같은 오리진에 남의 프로젝트 페이지가 섞이고,
   `github.io`는 도메인 신뢰도가 프로젝트별로 쌓이지 않는다. 커스텀 도메인이 SEO의 전제다.
3. 색인 상태를 **주기적으로 확인할 수단이 없다** — 지금은 배포 성공만 보고 있다.

**할 일**
- [내가] 라이브체크에 색인 관련 회귀 항목 추가: canonical 자기참조 여부, hreflang 상호참조,
  sitemap URL이 전부 200인지(죽은 URL이 sitemap에 있으면 신뢰도가 깎인다).
- [대표] **도메인 구매 → Search Console(+Bing·Naver) 등록.** 이게 늦어질수록 전부 늦어진다.

> 냉정한 판단: 도메인 없이 지금 도구를 더 만드는 건 **재고를 쌓는 것**이다.
> 팔 곳이 생기기 전까지 재고는 가치를 만들지 않는다.

## 2. 변환 매트릭스 (A안) — 조건부 착수

앞선 기획의 A안은 여전히 최대 레버지만, **전제가 색인**이다.
- 색인이 확인되기 전에 12페이지를 더 찍으면, 잘 되는지 안 되는지 알 수 없는 상태로 표면만 늘어난다.
- 반대로 색인이 확인되면 이건 **가장 싼 확장**이다(엔진 재사용, 페이지당 고유 키워드 1개).

**착수 조건**: Search Console에서 기존 도구 페이지가 **색인됨**으로 확인될 것.
**1차 범위**: 검색량 상위 12조합만. 조합별 고유 문단을 못 쓰면 그 조합은 만들지 않는다(thin content 강등 방지).

## 4. 이번에 드러난 구조적 교훈 3가지 (재발 방지 반영 완료)

작업하면서 실제로 물린 것들이다. 전부 같은 형태 — **"나열 방식"이 조용히 새는 구멍을 만든다.**

| 사고 | 원인 | 고친 방식 |
|---|---|---|
| `.github/workflows/*.yml`이 공개 사이트로 배포됨 | 빌드 SKIP이 **이름 나열** | "점으로 시작하면 제외"라는 **규칙**으로 교체 |
| `/img/` 서비스워커가 `/pdf/` 캐시를 삭제 | 캐시 이름이 빌드ID만 | 캐시명에 **스코프** 포함, 같은 스코프만 삭제 |
| 서명키를 만들지 않고 건너뜀 → 로그인 불가 | `convex env get`이 없어도 **exit 0** | 종료코드가 아니라 **출력 유무**로 판단 |

→ 원칙으로 승격: **"목록으로 막지 말고 규칙으로 막는다."** 새 항목이 생겼을 때
조용히 새는 쪽이 아니라 시끄럽게 걸리는 쪽으로 설계한다.

## 6. 대표 확인 필요 — Doppler 최소권한

새 `modutool` 프로젝트가 ops 프로젝트를 복제해 만들어진 것으로 보인다.
이 앱이 **쓰지 않는 키가 18개** 들어 있다:

```
ALIGO_API_KEY  ALIGO_TEST_MODE  ALIGO_USER_ID  ANTHROPIC_API_KEY
COUPANG_PROXY_SECRET  COUPANG_PROXY_URL  CRON_SECRET
KAKAO_SMTP_FROM  KAKAO_SMTP_PASS  KAKAO_SMTP_USER
NAVER_CLIENT_ID  NAVER_CLIENT_SECRET  RESEND_API_KEY
RG_ORDERS_SYNC_ENABLED  RG_STOCK_SYNC_ENABLED  SMS_SENDER
SUPABASE_SERVICE_ROLE_KEY  SUPABASE_URL
```

modutool이 실제로 쓰는 건 `CONVEX_DEPLOY_KEY` 하나뿐이다(+ 향후 광고·구글 OAuth 키).
**토큰으로 읽을 수 있는 범위 = 토큰 유출 시 노출 범위**라, 분리한 의미를 살리려면 지워야 한다.
`doppler-check` 워크플로가 이제 이 목록을 매번 출력하므로 정리 후 재실행으로 확인 가능하다.

> 값 자체는 워크플로 로그에 절대 찍히지 않는다(이름만 출력). 다만 SUPABASE_SERVICE_ROLE_KEY 같은
> 전권 키가 다른 앱 토큰으로 읽히는 상태는 그 자체로 정리 대상이다.
